# A locked screen vs the voice chats - test harness

The bug (a tester's report): in Daily -> Chat with DuSu, lock the phone, unlock, and the mic and Reply are dead until the chat ends. The page used to run `stopAllVoice()` on "hidden" (recogniser dropped, `running = false`, socket closed and nulled) and nothing handled the screen coming back. Now every voice chat is **paused**, not ended (`VP` in `backend/test_client.html`), and a socket that did not survive is replaced by a **quiet reconnect**:

* Daily Talk and Learn: `start {reconnect: true}` -> `daily_resumed` / `ready` (the first release, CLAUDE.md section 21).
* Face-to-Face, Interview, a Practice Room conversation (viva / discussion / custom) and the Home chat - the screens that share `#session`: `start {reconnect: true, resume: [the lines on screen], elapsed}` -> `session_resumed` (no opener, no model call, only new turns are counted). The page keeps the `start` frame the chat opened with, reads the lines back from the chat on screen, re-sends a line DuSu had not answered yet, and finishes an End that was pending (CLAUDE.md section 21, "the other chats").

Everything runs in Docker on **scratch** infrastructure - never the app's own `dusu-db-1`, never a real provider key (the scripts blank every key) and **no route to the internet** (the scratch Postgres network is `--internal`). Providers are the scripted fakes of `tests/keys/world.py`; the browser specs reuse `tests/keys/e2e_server.py` (the real app + a scratch Postgres; it seeds learners `lk1`..`lk40` for these specs).
One-time setup (the Playwright modules and the `dusu-ri-test` image) is the same as `tests/notify/README.md`.

## How the lock is simulated (`browser/lib.cjs`)
* `window.__setHidden(true|false)` overrides `document.hidden` / `visibilityState` and fires `visibilitychange` - what Chrome does on a lock. The fake `SpeechRecognition` refuses to start on a hidden page and ends a live recognition when the page becomes hidden, like a real browser; `window.__hold = true` makes it listen until the spec speaks (`window.__say`) - the state a learner is in when the screen locks.
* The speech stub has a controllable length (`__ttsMs`) and records what was spoken while hidden (`__spokenHidden`).
* `L.proxy(ctx)` sits between the page and the real server (Playwright `routeWebSocket`): every frame in both directions is recorded per connection, inbound frames can be HELD (`c.hold`, `c.holdIf(j)` for only some, `c.release()`), the connection can be KILLED (`c.kill()`), or FROZEN (`c.frozen = true`: both directions dropped while the page still believes the socket is open), and a new connection can be REFUSED (`P.refuse = true`: the socket opens and dies).
* Scenarios that need time to pass (the ping after a long lock, the 10-minute grace timer) install the Playwright clock (`{ clock: true }`) and `fastForward` it.
* `L.openTalk / openInterview / openViva / openHome` drive the real screens; `L.saySess` speaks one turn and waits for DuSu's reply; `L.settled()` waits until the server has stopped making model calls (an end-of-session save is itself a model call).
* `POST /__world/chatdone {on}` (test process only) makes the next plain chat reply the interviewer's closing line.

## Notes that cost time once
* A scenario that kills a socket must wait for the server's end-of-session save (itself a model call) before it measures "no model call for the reconnect": poll XP (Daily) or use `L.settled()`.
* Wait for the second connection's `start` frame before reading it - the connection record exists a moment before the page sends the frame. `P.holdNew` holds EVERY new connection: clear it once the first one exists, or the reconnect's `session_resumed` is held too.
* The speech watchdog in `say()` is `3500 + len * 90` ms: a "nothing is spoken while hidden" check must keep the page hidden for longer than that (A3 locks for 5 s).
* Each scenario uses a learner of its own; the rewards scenarios compare XP and need one to themselves. A trivial scripted chat earns 0 XP with the fake model scores - assert on the reward CALL (the selftest spies on `db.award_speaker_progress`), not on an XP delta, for Face-to-Face / Interview.
* The e2e server reads `backend/test_client.html` per request: do not edit it while a browser run is in progress.
* Do not put a trailing `&` on a command that is already run in the background by the tool: it detaches and the "completed" notification fires at once.
