# Keys / Install / Community - test harness

Everything runs in Docker on **scratch** infrastructure - never the app's own `dusu-db-1`, never a real provider key (`run.sh` / `browser/run_real.sh` blank every key; the bind-mounted `backend/` holds the real `.env`) and **no route to the internet**: the scratch Postgres network is created `--internal`, so even a bug cannot spend a real key. Every AI provider is a **scripted fake** (`world.py`): the app's SDK clients and probes are pointed at an `httpx.MockTransport` through `openrouter_provider._http_client_factory`, and each answer is scripted per provider host + bearer key. The error bodies are synthetic (a day limit cannot be provoked on demand); `capture_real_errors.py` is the owner-run script that records real ones with the owner's own keys so the fixtures can be checked against reality.
Same shape as `tests/notify/` (see its README for the one-time Playwright / test-image setup).

### What the code does (one screen)
* **Registry** - `config.KEY_PROVIDERS`, `providers_from` (base_url, models in order, `extra`, `chat_extra`), models in `_CLOUDFLARE_MODELS` / `_ZAI_MODELS` / `_SARVAM_MODELS`. Cloudflare's key is ONE string `"<account id>:<token>"` (`split_cloudflare` / `join_cloudflare`; split at the FIRST colon; the id must be exactly 32 hex characters because it goes into a URL path); the entry carries `key` (the identity: fingerprint, ledger, client cache) and `api_key` (the token: what goes on the wire).
* **Classifier** - `_specific()` reads each provider's own codes (`_codes()` collects every `code` in a body); only POSITIVE evidence marks a key invalid; Z.ai 1113 (HTTP 429) is `needs_credit`, not a limit; Cloudflare 3040 is scope `upstream` (the model, not the key); Z.ai / Sarvam day limits show NO reset time (`PUBLISHED_RESET` lists who publishes one).
* **No zero-quota probe exists** for the three: `probe.AUTH_PROBE` lists only Groq / Gemini / OpenRouter, so saving, Test and a re-check make the ONE real call, only a real answer (or a limit) is stored, a hiccup / an empty answer / "model gone" stores nothing (`unreachable`), out of credit is told apart (`needs_credit`), and a shallow re-check never spends a limited key's allowance.
* **Why no Cloudflare token-verify probe:** `GET https://api.cloudflare.com/client/v4/user/tokens/verify` (Bearer header, `{"success": true, "result": {"status": "active"}}`) does exist (developers.cloudflare.com/api/resources/user/subresources/tokens/methods/verify/), with the token in the header only. It is NOT used: it verifies a USER token (the page documents no account-owned-token equivalent), says nothing about the account id or the Workers AI permission, and a false "invalid" for a perfectly good account-owned token would keep a learner out. The one real chat call decides.
* **Order** - last in the chain, and `gate.PROVIDER_PRIOR` starts them in a lower health band (0.7 -> band 2; the others are in band 3, and a new provider can climb to band 3 but never above it), so an established provider answers first until it is actually doing badly. With `chain_v3` on, a broken reply from one of them is a failure like any other and the next provider answers in the same call (`chain_unit.py` I, `chain_ws.py`).
* **UI** - `KY` module: `MAIN` / `EXTRA` / `ORDER`, `NAME`, `FIELD`, `GETURL`, `AV`; a collapsed "More free options" in the wizard (three cards, Cloudflare has two boxes) and in the manage screen (opens by itself when a learner already uses one of them); the card hands its value to the same `saveKey()` through the hidden Keys-screen boxes (one code path stores a key); `ksGemSkip` now says "any two free services will do". `privacy.html` names the three providers; `sw.js` = dusu-v44.

## How the fake world works
`e2e_server.py` also has two behaviours for the "AI busy" work: `chat_down` (chat answers 503 but the zero-quota key checks answer ok: the KEY is fine, the AI is not) and `forbidden` (chat answers 403 with Google's "free tier is not available for this project" while the list still answers ok), and a test-only `POST /__world/serverhealth` that looks at DuSu's own keys at once (the real loop does it every 10 minutes).

`world.World` records every call as `(provider, key, kind, model)` and answers from a script: `world.on(provider, key, R, R, ...)` (the LAST step repeats; `kind="models"|"key"|"chat"` scripts one endpoint only); `world.default_chat` / `world.chat_reply(messages, provider, key)` answer anything unscripted. `e2e_server.py` wraps it as `Control`: a behaviour per provider (or exact key) - `ok / limited / limited_min / upstream / invalid / expired / down / unreachable` - flipped from the browser spec through test-only routes (`POST /__world/behave|reset|calls|flush|pushes`, never part of the app). The push service is a fake too (`/__world/pushes` returns what it was asked to send).

## Notes that cost time once
* A concurrent test only interleaves if the fake takes time: an immediate answer lets one task finish before the next starts (`R(200, ..., delay=0.15)`).
* `ctxFor(... { seed })` in `browser/lib.cjs`: the installed context seeds ONE time per context; pass `seed` AFTER the defaults (`Object.assign({...}, o, { seed })`) or a caller's seed replaces them.
* The re-check endpoint is limited to 4 a minute per learner and saving to 8: a spec that clicks Test / Check all more than that must use another learner (or expect the "wait a moment" message).
* A learner whose keys were left rejected by an earlier section gets the key pop-up on Home load (rightly): dismiss it first (`L.closePop`) or use a fresh learner.
* The new features default to Hindi unless the learner chose English on the server: the browser specs call `POST /lang` for every learner first.
* The key engine is switched per learner (`key_health` off / owner / on): with it OFF the walker, the precedence and every frame are exactly today's - tiers 2, 3 and 6 pin that.
